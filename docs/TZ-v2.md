# ТЗ v2: коннекторы NextLife — до опубликованных объявлений

Nov 5, 2026 · @User

## 1. Почему ничего не опубликовано и что меняется

В прошлом запуске ни одна форма публикации не была отправлена. Отчёт от 2026-11-05 честный, но 10 из 12 блокеров в нём агент мог снять сам, а владельцу передал как задачи.

Причины, взятые из отчёта `reports/final.md`:

- Служба `nextlife-web` работает с `NEXTLIFE_PUBLISH_DRY_RUN=1`, и код этого репозитория в неё не выложен. Боевая публикация отключена на уровне службы.
- У агента нет прав: он не читает `/etc/phonebroker/broker.yaml` и фото лота, не ставит пакеты, не создаёт таймеры systemd, не перезапускает службу.
- Агент останавливался на первом препятствии в UI (вкладка «Můj profil» в Sbazar, дерево категорий Vinted) и не пробовал другие способы.
- Отсутствующие данные (цена в EUR) и решения по чужим объявлениям агент переадресовал владельцу, хотя они уже определены в ТЗ.
- Публикацию проверяли скриптами агента, а не тем путём, которым ей пользуется программа.

Что меняется в v2:

1. Агент получает sudo на vzu5-wall на время задачи и сам чинит окружение (раздел 2).
2. Всё, что не входит в закрытый список дел владельца, агент решает сам: документация, поиск в интернете, разные подходы (раздел 3).
3. Приёмка — полный цикл «опубликовать → изменить → снять → опубликовать снова» через развёрнутую службу NextLife, тем же путём, что и кнопка в веб-интерфейсе (раздел 5).
4. В программе появляется постоянная «Карта коннекторов»: по каждой площадке видно, работает она или нужна помощь владельца и какая именно (раздел 7).
5. Работа идёт в две фазы с одним сообщением владельцу между ними (раздел 8).

## 2. Права и окружение

На время задачи у агента (пользователь `user` на vzu5-wall) есть sudo без пароля через `/etc/sudoers.d/90-nextlife-agent`. Последнее действие задачи — `sudo rm /etc/sudoers.d/90-nextlife-agent` и проверка, что `sudo -n true` больше не проходит.

С sudo агент делает сам:

1. **Деплой.** Пишет `scripts/deploy.sh`: выкладывает код репозитория в службу `nextlife-web`, применяет миграции, перезапускает службу, ждёт health-check на порту 8081, при провале откатывает на прошлую версию. Скрипт запускается одной командой и остаётся владельцу для будущих обновлений.
2. **Боевой режим.** Убирает `NEXTLIFE_PUBLISH_DRY_RUN=1` из unit-файла, `systemctl daemon-reload`, перезапуск, проверка через `systemctl show nextlife-web -p Environment`.
3. **Права файлов.** Публикацию выполняет служба от своего пользователя `nextlife`, поэтому доступ к фото лотов нужен ей, а не агенту. Агенту для отладки чтение даётся через группу или ACL; права службы не расширяются сверх нужного.
4. **Пакеты.** Ставит всё, что нужно консоли входа (Xvfb, x11vnc, websockify, noVNC или их аналоги для AlmaLinux 10 из AppStream и EPEL). Точные имена пакетов агент находит сам.
5. **Конфигурация PhoneBroker.** Читает и правит `/etc/phonebroker/broker.yaml`, перезапускает брокер, проверяет, что аренда PropertyBoss проходит.
6. **Таймеры.** Создаёт systemd-таймеры для перепроверки модерации и регулярной проверки коннекторов (раздел 7).

Запрещено и с sudo: трогать службы, не относящиеся к NextLife и PhoneBroker (SimBridge, Tailscale и другие), менять сетевые настройки и firewall, кроме открытия консоли входа только для tailnet, удалять данные других проектов. Каждая команда с sudo пишется в `evidence/_system/sudo.log` с временем и целью.

## 3. Протокол решения проблем

Любое препятствие агент решает сам, если оно не входит в закрытый список 3.1. Передать владельцу проблему не из списка — то же нарушение, что и ложный успех.

**3.1. Закрытый список дел владельца.** Только эти пункты агент вправе передать владельцу:

1. Ввести логин, пароль, код 2FA или SMS-код, пришедший на личный телефон владельца.
2. Создать аккаунт на площадке, где его нет и регистрация требует личных данных владельца.
3. Заплатить деньги (платное размещение, платная функция).
4. Принять товарное решение, которого нет в разделе 4: цена, выбор вещи для продажи, условия сделки.
5. Вручную выполнить действие, автоматизация которого запрещена правилами площадки (Facebook).

Всё остальное — права, пакеты, конфигурация, код, UI-автоматизация, разбор формы, ошибки площадки, отсутствующие поля в модели данных — решает агент.

**3.2. Порядок решения.** Для каждого препятствия агент проходит шаги и записывает каждый в `evidence/<platform>/<run_id>/attempts.md`:

1. Прочитать собственные логи, дамп UI, HTML, текст ошибки.
2. Прочитать документацию: `man`, `--help`, документацию библиотеки (Playwright, uiautomator2, adb), справку площадки.
3. Искать в интернете: точный текст ошибки, название приложения и экрана, форумы, issues на GitHub, Stack Overflow.
4. Попробовать разные подходы — не меньше 5 различных, а не повторов одного: поиск элемента по `text`, `content-desc`, `resource-id`, прокрутка, deep link приложения, веб-версия площадки вместо приложения, изменение порядка шагов.
5. Только после 5 разных подходов без результата — статус «Не решено агентом» с полным описанием (раздел 8.3).

**3.3. Не останавливаться на одной площадке.** Нерешённое препятствие на одной площадке не останавливает работу: агент переходит к следующей и возвращается позже с новым подходом.

**3.4. Не спрашивать уже решённое.** Перед тем как задать вопрос владельцу, агент проверяет раздел 4 и ТЗ от 4 ноября. Вопрос, ответ на который там есть, не задаётся.

## 5. Полный цикл приёмки на боевом пути

Коннектор работает, только если весь цикл управления объявлением прошёл через развёрнутую службу `nextlife-web` в боевом режиме. Прогон скриптом агента в обход службы приёмкой не считается.

**5.1. Боевой путь.** Каждое действие запускается через HTTP API службы — тот же эндпоинт, который вызывает кнопка в веб-интерфейсе. Служба сама арендует телефон у PhoneBroker или берёт сохранённую веб-сессию, сама читает фото лота. Агент только вызывает API и читает результат.

**5.2. Шаги цикла для лота #130 на каждой площадке.** Каждый шаг подтверждается верификатором `nextlife/verify/live_listing.py` в чистом контексте без сессии.

1. Опубликовать → LIVE\_VERIFIED по всем условиям раздела 3.2 ТЗ от 4 ноября.
2. Изменить: добавить в конец описания строку `Aktualizováno <дата>` → верификатор видит новую строку на публичной странице.
3. Вернуть исходное описание → верификатор видит исходный текст.
4. Снять объявление → публичный URL больше не показывает объявление.
5. Опубликовать снова → новый URL, LIVE\_VERIFIED.
6. Объявление остаётся опубликованным: вещь продаётся.

Если площадка запрещает повторную публикацию сразу после снятия, агент фиксирует это с доказательством, ждёт требуемый срок и выполняет шаг 5 позже в этой же задаче или в Фазе B.

**5.3. Итог по площадке.** Статус «Работает» в Карте коннекторов ставится, только если пройдены шаги 1–5 и после них есть живое объявление. Пройдены не все шаги — статус «Не решено агентом» или «Нужна помощь владельца» с номером шага, на котором остановилось.

**5.4. Лимиты.** На одну площадку — не больше 3 публикаций за сутки, включая шаг 5. Дефект (чужие фото, неверная цена) — немедленное снятие по разделу 3.3 ТЗ от 4 ноября.

## 7. Карта коннекторов в программе

В веб-интерфейсе NextLife появляется постоянная страница `/ui/connectors`: по ней владелец в любой момент видит, какие площадки работают и где нужна его помощь. Это функция программы, а не одноразовый отчёт.

**7.1. Состояния площадки.** Ровно одно из четырёх:

| Состояние | Когда ставится | Что видит владелец |
| --- | --- | --- |
| Работает | Полный цикл 5.2 пройден, последняя проверка 7.2 успешна | Дата проверки, ссылка на живое объявление |
| Нужна помощь владельца | Препятствие из списка 3.1 | Одно действие простыми словами и кнопка или ссылка, где его выполнить |
| Не решено агентом | Техническое препятствие, 5 подходов не помогли | Шаг цикла, на котором остановилось, текст ошибки, что пробовали, ссылка на доказательства |
| Только поиск | Публикация вне задачи или запрещена правилами | Причина со ссылкой на доказательство |

Состояние вычисляется кодом из реестра доказательств и результатов проверки 7.2, вручную не выставляется.

**7.2. Регулярная проверка.** Systemd-таймер раз в сутки и кнопка «Проверить сейчас» на странице запускают проверку по каждой площадке:

- сессия или вход в приложение действительны (без публикации);
- все живые объявления NextLife открываются верификатором и совпадают с карточками;
- поиск возвращает реальные объявления по запросу (3 ссылки).

Истёкшая сессия переводит площадку в «Нужна помощь владельца» с кнопкой входа; пропавшее объявление — в «Не решено агентом» с причиной.

**7.3. Управление объявлениями.** В карточке лота — список его объявлений по площадкам со статусом, ссылкой и кнопками «Изменить», «Снять», «Опубликовать снова». Кнопки вызывают тот же API, что прошёл приёмку 5.2.

## 8. Фазы, остановка и сообщение владельцу

Задача выполняется в две фазы. Между ними владелец получает одно сообщение и выполняет только пункты из списка 3.1.

**8.1. Фаза A.** Агент выполняет по порядку:

1. Окружение (раздел 2): деплой, боевой режим, права, пакеты, консоль входа, PhoneBroker.
2. Поле цены EUR и остальное из раздела 4.
3. Карта коннекторов и регулярная проверка (раздел 7).
4. Полный цикл 5.2 на каждой площадке, где не нужен владелец.
5. На площадках, где нужен владелец, всё готово до момента его действия: консоль открывается, приложение открыто на нужном экране, форма заполнена.
6. Сообщение владельцу (8.3) и отчёт.

**8.2. Когда Фаза A считается законченной.** Только когда по каждой площадке выполнено одно из трёх: «Работает»; «Нужна помощь владельца» с пунктом из списка 3.1; «Не решено агентом» после 5 разных подходов, записанных в `attempts.md`. Завершать Фазу A раньше запрещено, даже если прошло много времени.

**8.3. Сообщение владельцу.** Генерируется скриптом из Карты коннекторов, появляется на `/ui/connectors` и в Telegram, если бот задан. Строго в этом виде:

```markdown
## Работает
- Bazoš.cz — https://... (проверено 2026-11-05 14:20)

## Нужно ваше действие (около N минут)
1. Aukro: войдите в Manažer prodeje — открыть: http://<адрес консоли>/ui/connect?platform=aukro_cz
2. Sbazar: введите код из SMS в приложении — откройте ярлык «Телефон», экран уже открыт

## Не решено агентом
- Vinted, шаг 4 «Снять»: <ошибка>. Пробовали: <5 подходов кратко>. Доказательства: <путь>

## Только поиск
- Kleinanzeigen.de, Willhaben.at, OLX.pl — публикация вне задачи
```

Каждый пункт «Нужно ваше действие» — одно действие, ссылка, где его сделать, оценка времени. Технических терминов, путей к файлам и вопросов из раздела 4 в нём нет.

**8.4. Фаза B.** Запускается фразой владельца «Продолжи ТЗ v2, Фаза B». Агент проверяет, что действия владельца выполнены (вход действителен), проходит полный цикл 5.2 на оставшихся площадках, ещё раз пробует пункты «Не решено агентом» новыми подходами, обновляет Карту коннекторов, удаляет свой sudo и выдаёт итоговый отчёт.
